## 一、队友第二问模型总结

一句话概括：**把"单星巡游观测 30 颗目标"翻译成一个字典序优化问题，再用"结构分析降维 + 两层求解"绕开直接混合整数非线性优化的规模灾难。**

### 1.1 问题本质与建模

30 颗目标都是近圆近赤道 GEO 星，分布在 r1 东西两侧 ±19° 经度带，半长轴与 r1 相差通常不到 3 km——不机动几乎没有相对漂移。所以问题本质是**沿同步轨道带的巡游**：r1 靠少量机动调整漂移速度，依次飞抵目标，在满足观测几何时完成连续 60 s 观测。

- **决策变量**：观测事件序列 E = {(j_k, s_k)}（目标 + 开始时刻）和脉冲序列 M = {(τ_m, Δv_m)}（时刻 + 速度增量）。规定落在 (s_{k-1}+60, s_k] 内的脉冲归属第 k 次观测。
- **动力学**：无机动段二体方程 r̈ = −μr/‖r‖³，脉冲时刻位置连续、速度跳变 v⁺ = v⁻ + Δv；目标星不机动，二体传播。
- **观测可行谓词** O_j(s)：在整个 [s, s+60] 内同时满足 10 ≤ ‖ρ‖ ≤ 50 km、光照角 ≤ 45°、侦测角 ≤ 45°（沿用第一问定义，太阳/地心两个 45° 圆锥）。
- **优化模型**（字典序，不加权）：lex max (K, −Σ‖Δv_m‖)，约束为各次观测可行、目标互不相同、末次观测 ≤ 30 天、单次脉冲 ≤ 30 m/s、相邻脉冲间隔 ≥ 3600 s、累计 ≤ 300 m/s、每次观测最多 2 次脉冲。

### 1.2 模型最值钱的部分：结构分析

这是整个工作的核心洞察，把搜索空间从"天文数字"压到可算：

- **每颗目标每天只有一次观测机会**：r1 倾角 4.38°、目标约 0.2°，轨道面夹角 4.2° 对应法向振幅约 3000 km ≫ 50 km 上限，只有目标穿越 r1 轨道面时可能；再叠加"太阳与地心夹角 ≤ 90°"的光照必要条件再砍一半。于是 30 天内全部候选事件约 1000 个。（b7 几乎共面，是例外。）
- **漂移相位模型**：以 r1 初始角速度为参考定义相位，观测要求 r1 在时刻 s 追上目标（相位相等）。漂移率与半长轴偏差成正比，ω ≈ −540 Δa/a（°/天），所需切向增量 Δv ≈ (n/2)|Δa|，即 k ≈ 2.85 m/s per (°/天)——巡游燃料几乎全花在改变漂移率上。
- **公共交点方向**：切向脉冲把轨道拱点放在脉冲方向，交会方向地心距才能与目标对齐。18 颗目标的交线方向集中在 r1 轨道面内 31°–37° 的窄带，可以高漂移率依次扫过、每次只需小修正；另 6 颗（b6、b16、b21、b22、b25、b30）偏离大、代价明显高。这决定了巡游路线的形状——先西扫、约第 8.5 天折返、再东扫。

### 1.3 两层求解算法

- **第一层 · 相位模型束搜索排日程**：在约 1000 个候选事件上逐日扩展，由相位条件反推所需漂移率，单脉冲代价 k|ω_a−ω|、双脉冲代价 k(|ω_a−ω|+|ω_b−ω_a|)，其中 ω_b 上限由交线偏离公共方向决定。评价函数 = 累计代价 + 已用时间 + 剩余目标所需最小巡游角度（最后一项防止把时间耗在一侧）。纯代数扩展，束宽可取上万。
- **第二层 · 逐段精确求解**：按日程逐段解，每段就是"以上次观测末态为初值的一个问题一"，变量 (t₁, t₂, Δv₁, Δv₂, s)，在完整二体 + 1 s 网格约束下用 SLSQP 最小化两次 Δv 之和，再在 0.05 s 网格认证；初值由状态转移矩阵线性化瞄准给出，脉冲时刻候选取在交会方向前若干半圈（切向效率最高）。某段排定日失败就自动改用相邻日的观测机会。**每段用精确终端状态接力，所以最终方案对完整模型严格可行，不依赖第一层的近似**——这是两层架构的关键正确性保证。
- **同次飞越双目标（30 颗全覆盖的临门一脚）**：b19 与 b20 经度只差 0.03°，第 23 天穿过 r1 轨道面的时刻差约 13 分钟。把它们写进同一个优化问题、机动变量只有一组、对两个目标各写一遍观测约束，结果先观测 b19 再观测 b20，只比单独观测 b20 多 0.23 m/s——省下一整天，凑齐 30 颗（b19 因此没有自己的专属脉冲，沿用 for=b20 的那次）。

### 1.4 结果与评价（截至当时的 30 颗版本）

方案 30/30 全覆盖，累计 Δv **177.26 m/s**（预算的 59%），58 次脉冲（48 次 >1 mm/s），单次最大 28.18 m/s，间隔 ≥ 3600 s，末次观测第 29.52 天。求解时统一留余量（距离离边界 ≥ 0.5 km、角度 ≤ 44.5°、连续 62 s），并经过三种独立方式复核（解析重放、ERFA 几何/视方向双口径、ATK 分段接力），都是 30/30。

**模型的诚实边界**：观测数已达上限 30，第一优先级确为最优；但累计 Δv 是启发式日程下"逐段最优"，**没有全局最优性保证**。论文自己点名的降本方向是：重排高代价观测的日期（b6、b17、b21、b23、b7）、去掉余量重新求解、相邻段联合优化。

> 注：队友后续已迭代到 M2-B（全计划凸优化 SCP + 大邻域搜索 LNS），当前采用方案见 `solutions/README.md` 与 `最新代码地图.md`；本节总结的是 v6/逐段 SLSQP 时期的模型脉络，算法骨架依然适用。

## 二、代码数据接口与可移植性评估

结论：**接口是"半开放"的——换一份同结构的数据（比如像任务 16 那样只是数值精度更新）能跑通；但换一组差异较大的数据，"直接换数据就出好效果"目前做不到。**

### 2.1 做得好的部分（数据驱动）

| 环节 | 情况 |
|---|---|
| 一问求解 | `code/p1/solver.py` 有 `--data` 参数，直接读 `data/数据.xlsx`，底层 `datafile.read_states()` 还能自动识别 km/m 单位——换数据只改一个参数 |
| 验证端 | `tools/verify_p2.py` 从方案 JSON 里读 `r1_km`/`targets_km`，数据随方案自带，验证脚本完全数据驱动 |
| p2lib 接口 | 有 `P2_INIT`（换观测星初值）、`P2_TARGETS`（筛选目标子集）两个环境变量钩子 |
| 数据核对 | `dump_data.py` 能从 Excel 导出全精度 CSV 供比对 |

### 2.2 真正的断点：数据链路断了

**二问/三问的求解器根本不读 `data/数据.xlsx`，而是读各目录里手抄的 `states.json`。** 查到 6 份副本，而且已经分裂成两个版本：

```
b8461a62…  code/p2/batch/states.json, code/p3/states.json, v2/states.json   ← 旧数据
b4d9471d…  code/p3/v3/states.json, v4/states.json, v5/states.json           ← 新数据（v3/v5 当前采用）
```

`data/数据.xlsx` → `states.json` 这一步**没有任何自动化工具**——`dump_data.py` 只导出给人看的 CSV。任务 16 换数据时，这些 JSON 是手工同步的。所以现在换数据，要么手动改 6 份 JSON，要么自己写转换脚本；漏改一份就会出现"用新数据验证、旧数据求解"的隐性错误。

### 2.3 更深的问题：算法里有"数据特定"的先验

这才是"换数据还能出好效果"的核心风险。代码把这套数据的结构特征写成了常量：

- `sched.py` 里的 **36.8°**——r1 轨道面内目标交线方向的公共带中心，用来判断哪些目标能高漂移率交会、给它们放宽漂移率上限（wmax）。这值是从当前 30 颗目标算出来的先验，换一批目标分布就得重算，否则束搜索排程质量会明显下降。
- 历元 **2027-01-01**、时长 `T_END=2592000`、太阳星历样条基准，全硬编码在 `p2lib.py` 里；换任务历元要改代码。
- 三问 v6 的 δa=5.90 km 是"取目标半长轴最大偏离"这个**论证结论**，换数据要重新论证，不是改个数字就行。

所以：换一组"同样是 GEO 近赤道带、30 颗左右"的数据，算法骨架仍适用（历史证明过，任务 16 就是这么做的）；如果目标数量、分布带、历元大变，`36.8°` 这类先验和 δa 依据会失效，算法能跑但"好效果"没有保证。

### 2.4 要真正做到"换数据即用"，需要补三样东西

1. 一个 `xlsx → states.json` 的生成脚本，让求解器直接读 Excel（或至少一键生成唯一一份 states.json），删掉 6 份副本，改成单一数据源；
2. 把历元/时长/μ/约束从 p2lib 提到配置（环境变量或 config 文件），`36.8°` 改成运行时从当前目标状态自动算交线带，而不是写死；
3. DATA 版本指纹：求解结果 JSON 里记下所用数据的哈希，复核时校验，避免数据版本错配。

## 三、ATK Connect 模式二次开发分析

### 3.1 Connect 模式的本质

Connect 是**进程间通信**：脚本通过 TCP 连到**已经打开的 ATK 界面**，发文本命令让 ATK 执行，ATK 返回数据。它和之前用的 Component 模式（进程内加载 DLL，`code/atkbridge.py`）是两条不同的路：

| | Connect 模式 | Component 模式（现在用的） |
|---|---|---|
| 通信 | TCP 网络协议，文本命令 | 进程内 SWIG 对象调用 |
| ATK 状态 | **必须先打开 ATK 图形界面** | 无需 GUI，后台 DLL |
| 接口 | `atkOpen/atkConnect/atkClose` 三个函数 | `root.ExecuteScript()` / 对象属性 |
| 稳定性 | 全图形环境，不易卡死 | 任务 11 遇到的弹窗阻塞就出在这 |
| 多语言 | Python/Java/Matlab/C++ 都有官方包 | 主要 Python/Java |

最相关的价值：**Connect 每次命令独立、走 GUI，可能绕开之前批量建对象时属性页弹窗卡死的问题**。

### 3.2 Python 调用流程（官方标准写法）

核心只有三个函数（来自 `ATKConnectPython.py` 的 SWIG 导出）：

```python
import sys, os, time
sys.path.insert(0, <ATK安装目录/Help/Examples/08-二次开发案例/Python>)  # 或 vendor_samples 副本目录
from ATKConnectPython import atkOpen, atkConnect, atkClose

# 1. 先手动打开 ATK（或让脚本 Popen 启动），循环等待连接
conID = -1
for i in range(30):
    conID = atkOpen('127.0.0.1', 6655)   # 返回 >0 的连接号即成功
    if conID > 0: break
    time.sleep(1)

# 2. 发命令：atkConnect(连接号, 命令类别, 命令参数)
atkConnect(conID, 'New', '/ Scenario Demo')
atkConnect(conID, 'New', '/ Satellite Sat1')
atkConnect(conID, 'SetState', '*/Satellite/Sat1 TLE "1 54216U..." "2 54216..."')
atkConnect(conID, 'Access', '*/Satellite/Sat1 */Satellite/Sat2 TimePeriod "14 Mar 2024..." "21 Mar 2024..."')
atkConnect(conID, 'SAve', '/ *')

# 3. 关闭
atkClose(conID)
```

`atkConnect(conID, command, path)` 的 `command` 是 ATK 命令名（`New`/`SetState`/`Access`/`Astrogator`/`Animate` 等），`path` 是"对象路径 + 该命令的参数串"，语法与 STK Connect 高度相似——`*/Satellite/xxx` 路径写法可以直接用。

### 3.3 命令能做什么（官方示例覆盖的能力）

官方 `ATKConnectPythonTest.py`（322 行）里的命令集，覆盖了二次开发的典型场景：

- **建场景/设时段**：`New / Scenario X`、`SetAnalysisTimePeriod * "5 Nov 2022..." "7 Nov 2022..."`
- **建卫星/设轨道**：`New / Satellite X`、`SetState */Satellite/X TLE "..."`（TLE）、`Astrogator ... SetValue ... Keplerian.sma/ecc/inc`（六根数）
- **机动规划（MCS）全序列**：示例完整演示了 `Astrogator ... InsertSegment ... Propagate/Target_Sequence/Maneuver`、`AddMCSSegmentControl`、`SetMCSControlValue` ——正是第一问/单星 MCS 场景做的事，可以直接照搬这套命令自动生成
- **访问计算**：`Access */Satellite/A */Satellite/B TimePeriod "..." "..."`
- **保存**：`SAve / *`

Java、Matlab、Octave 示例做的是同一套动作，只是调用语法不同。C++ 走 `ATKConnector.h` 静态库。

### 3.4 ⚠️ 一个必须注意的坑：端口

- 官方所有示例 `atkOpen('127.0.0.1', 6655)` —— 用 **6655**
- 本机 `D:\ATK\ATK4\ATK-4.2.0-rc.2\server_config.ini` 配的是 `port=8080`
- 之前探测记录 `report/env/probe_report.md` 显示 8080 连接超时（因为当时 ATK 没开）

**建议**：先手动打开 ATK，然后 6655 和 8080 都试一下 `atkOpen`，哪个返回正数用哪个；如果都不行，检查 ATK 界面"工具/选项"里有没有 Connect 服务开关。这是唯一需要在本机确认的一步。

### 3.5 实操建议

1. **先跑官方示例验证通路**：把 `D:\ATK\ATK4\ATK-4.2.0-rc.2\Help\Examples\08-二次开发案例\ATKConnectPythonTest.py` 和同目录的 `ATKConnectPython.py`、`_ATKConnectPython.pyd`、`ATKConnectorDll.dll` 拷到一个目录，打开 ATK，运行它，确认能连上、能建场景。
2. **Python 版本**：要用与 SWIG 模块匹配的版本；ATK 自带 Python 在 `ATK安装根目录\Python\_internal\python.exe`，实在不行用它跑。
3. **针对场景**：可以把 `tools/build_single_r1.py` 的 MCS 段序列生成逻辑，用 Connect 命令重写一遍（`Astrogator ... SetValue`），这样每次命令独立，不再出现 Component 模式下的属性页弹窗阻塞。
